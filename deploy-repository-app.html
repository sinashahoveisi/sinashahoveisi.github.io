01 / Architecture

Overall Architecture & Actors

There are three actors, each with its own independent API. The boundary of responsibility between them is exactly what this entire document is built around.

Actor Role
User's Browser Sends requests directly to both auth (GitHub connection and account/repo/branch browsing) and PaaS (creating and managing the application).
PaaS Only connects to auth when it needs to verify repo/branch ownership, obtain a clone-token, or manage a webhook — via /internal/... with the x-service-key header.
auth Has both a user-facing endpoint (session-based, for Connect and Browse) and an internal endpoint. It's responsible for GitHub OAuth, token storage, and proxying the GitHub API — not PaaS.

Dashboard domain: https://cloud.danaix.com/

Architecture Decision 01 GitHub connection and account/repo/branch browsing happen entirely directly between the Browser and auth. PaaS plays no role in the connect phase or the browse phase, and is unaware of the user's selection until the moment of submit.
Architecture Decision 02 user_id in PaaS and user_id in auth are the same. No mapping table is needed; PaaS passes its own user_id directly in calls to /internal/git/{user_id}/....
02 / Data

Database Tables

One new table in PaaS (repositories), three existing tables populated in the same create transaction, one Redis key for idempotency, and a set of OpenShift labels that underpin live queries.

REF auth.git_connections

Outside PaaS's ownership — reference only; stores each user's connection to a git hosting provider (e.g. GitHub). The schema is provider- and auth-mechanism-aware so a later GitHub App (or GitLab/Bitbucket) path does not force a breaking migration.

Schema deltas vs. the original model
  • Added auth_type (non-nullable) — distinguishes which auth mechanism the row uses. Today every row is provider = "GITHUB" and auth_type = "OAUTH".
  • access_token_encrypted changed from non-nullable to nullable — only populated for OAUTH-type connections; stays null for future installation-based rows.
  • Added installation_id (nullable) — reserved for future GitHub App (or other installation-based) support; unused/null for all rows today. Purely forward-compatible — not a behavior change.
  • No other columns change.

Because classic GitHub OAuth App tokens typically do not expire (unless the OAuth App has expiring-tokens explicitly enabled), token_expires_at will likely stay null for GitHub OAuth connections — but the column remains nullable and generic so it works correctly for providers that do return expiring tokens (e.g. GitLab).

GitHub OAuth App vs GitHub App — decision and tradeoffs

There are two distinct ways to integrate with GitHub for repository access. Neither is the same thing as the existing GitHub SSO login, which remains untouched either way — this is a separate, dedicated registration used only for repo access.

1. Classic GitHub OAuth App

Same family as the existing SSO integration, but with a different, dedicated OAuth App registration and a wider scope such as repo.

  • Connect flow: standard OAuth consent screen. The user approves once; access is all-or-nothing based on scope — the token receives access to all repositories the user can see (public and private), not a hand-picked subset.
  • Token lifetime: by default does not expire unless the OAuth App has "expiring tokens" explicitly enabled. A single stored token can therefore be reused indefinitely without re-fetching from GitHub.
  • Pros: simplest to implement — same pattern as the existing SSO integration, no extra signing/JWT logic, fastest path to an MVP.
  • Cons: a long-lived (potentially permanent) token with broad access sits encrypted in our database. If the database or backups ever leak, that token grants an attacker full access to the user's repos until the user manually revokes it — there is no automatic expiry safety net. There is also no per-repo access scoping; the user cannot limit which repos the connection can see.
  • Webhooks: must be created and deleted per repository individually (POST /repos/{owner}/{repo}/hooks). Every repo that wants auto-deploy-on-push needs its own webhook managed and cleaned up — this is the approach assumed by the resolve/delete flows elsewhere in this document.

2. GitHub App (installation-based)

  • Connect flow: the user is sent through GitHub's "Install App" flow instead of a plain consent screen, and explicitly picks either "all repositories" or a specific list the App may access. More transparent for the user, but one extra step compared to classic OAuth consent.
  • Token lifetime: installation access tokens are always short-lived (~1 hour). There is no long-lived user token to store — instead we store only the installation_id, and mint a fresh token on demand by signing a JWT with the GitHub App's private key each time one is needed.
  • Pros: much smaller security footprint — nothing long-lived and broadly scoped sits in our database; access is limited to only the repos explicitly granted at install time; a single App-level webhook can receive push events for all installed repositories at once, removing the need to create/track a webhook per repository.
  • Cons: extra one-time implementation cost (JWT signing with the App's private key to mint installation tokens, plus installation-management logic), and the connect UX has one more step for the user.
Decision (final, for now) Use classic GitHub OAuth App — for simplicity and fastest implementation. This is currently the only git provider being integrated, and time-to-ship matters more at this stage.

This decision is explicitly revisitable later. Because the internal /internal/git/... API contract exposed to the PaaS is provider-agnostic (the PaaS never sees raw tokens or provider-specific auth details — only repo, branch, clone-token, and webhook operations), switching the underlying GitHub auth mechanism later to a GitHub App would only require changes inside the auth service's GitHub provider-client implementation and the git_connections table. Nothing in the PaaS, and nothing in the API contract between the two services, would need to change.

03 / API

API Routes — with full schema

In order: user-facing on auth, internal on auth (PaaS only), and user-facing on PaaS.

auth · user-facing (directly from Browser)

GET /user/git/github/connect

Auth: the user's session in auth. Query: return_to (required) → https://cloud.danaix.com/git/callback

Response: 302 → GitHub's OAuth authorize URL (second-app client_id, scope=repo). Error: 401 if not logged in.

GET /user/git/github/callback

Parameters: code, state. The code is exchanged with GitHub, {id, login} is fetched, and the git_connections record is created/updated. 

Success: 302 → https://cloud.danaix.com/git/callback?status=success&account_id={uuid}
Failure: 302 → https://cloud.danaix.com/git/callback?status=error&reason={reason}
reason:  oauth_denied | token_exchange_failed | github_api_error
The GitHub token is never placed in the URL or passed to the Browser.

GET /git/accounts

Second step of the connect phase — called after returning to /git/callback?status=success, to confirm and display the newly connected account.

auth · internal (PaaS only, x-service-key header required)

POST /internal/git/{user_id}/accounts/{account_id}/repos/{repo_id}/resolve

Verifies account/repo ownership, verifies token validity, checks the branch exists on GitHub, and if auto_deploy_on_push=true, creates the webhook and generates a short-lived clone-token.

04 / Flow

Full Flow — from GitHub connection to execution on OpenShift

GitHub connect phase (one-time, directly between Browser and auth)

  1. Request connection

    The dashboard calls GET /user/git/github/connect?return_to=... on auth; auth returns a 302 to GitHub's consent URL.

  2. User approval

    The Browser goes to GitHub, the user approves.

  3. Return with code

    GitHub redirects the Browser to GET /user/git/github/callback?code=...&state=... on auth.

  4. Create connection

    auth exchanges the code, obtains a token, fetches {id, login}, and creates the git_connections record.

  5. Return to dashboard

    Redirect to .../git/callback?status=success&account_id=<uuid> — with no token in the URL.

  6. Final confirmation

    The dashboard's callback page calls GET /git/accounts and displays the newly connected account. If status=error is returned, this request is never made.

Browse phase (entirely direct, no PaaS involvement)

  1. List accounts

    The frontend calls GET /git/accounts directly on auth.

  2. List repos

    The user selects an account → GET /git/accounts/{account_id}/repositories

  3. List branches

    The user selects a repo → GET .../repositories/{repo_id}/branches

  4. Complete the form

    The user fills in the rest of the form (dockerfile_path, ports, routes, volumes, variables, scaling, plan). The frontend must keep the selected account_id, repository_id, and branch for the final submit.

Submit to PaaS phase — POST /applications/repository/

  1. Generate ID and callback_url

    PaaS pre-generates a repository_id (UUID) and builds the callback_url from it: https://cloud.danaix.com/applications/repository/webhooks/push/{repository_id}

  2. Validate with auth

    Before any DB write: POST /internal/git/{user_id}/accounts/{account_id}/repos/{repo_id}/resolve with {branch, auto_deploy_on_push, callback_url}. If valid: false, PaaS immediately returns an error and writes no rows.

  3. Write to DB (one transaction)

    repositories with the same pre-generated id, then applications (status=CREATING), application_deployments (status=PENDING, kind=DEPLOYMENT), and application_plans per the mapping table in section 2.

  4. Create on OpenShift

    In this order:

    # Object Key fields
    1 Secret basic-auth password = clone_token.value; must be replaced with a fresh clone-token before every rebuild
    2 ImageStream —
    3 BuildConfig source.git.uri=clone_url, ref=branch, sourceSecret, contextDir=build_context_path, dockerfilePath
    4 Secret/ConfigMap from variables, split based on is_secret
    5 Deployment image from ImageStream, command/args/readinessProbe, envFrom, container ports, resources from plan, replicas if MANUAL
    6 Service one ServicePort per ports item
    7 Route for each routes item; port.targetPort matched via port_name against the Service's port name; TLS fields
    8 PVC for each volumes item, mounted at mount_path
    9 HPA only if scaling.mode=AUTO; min/max replicas, CPU/Memory metric
    10 Start Build —
    11 Update application_deployments.name with the actual workload name after apply
  5. Celery polling

    Poll Build status, then Deployment rollout, updating applications.status and application_deployments.status (CREATING → ACTIVE/FAILED, PENDING → DEPLOYING → RUNNING/FAILED) — the same pattern as the catalog pipeline.

Delete phase — DELETE /applications/repository/{application_id}

  1. Find the repository record

    PaaS locates the related repositories record.

  2. Delete the webhook

    If webhook_id is non-null: DELETE /internal/.../webhooks/{webhook_id} — idempotent, must return 200 even if the hook no longer exists on GitHub.

  3. Clean up OpenShift

    Using label selector = danaix.com/application-id=<id>, all related objects (Service, Route, BuildConfig, ImageStream, Deployment, PVC, Secret, ConfigMap, HPA) are found and deleted.

  4. Soft-delete records

    applications, application_deployments, application_plans, repositories are marked following the deleted_at pattern.

05 / Validation

Request Validations

  • routes[].port_name must exactly match one of the values in ports[].name, otherwise 422.
  • If scaling.mode = AUTO, the min_replicas, max_replicas fields are required; replicas is ignored.
  • If scaling.mode = MANUAL, the replicas field is required; the AUTO fields are ignored.
  • application_plan.type must be one of CUSTOM/PACKAGE, and billing_type must be one of PAYG/FLAVOR.
06 / Optional

Separate Phase — auto_deploy_on_push

For when we also want the webhook call to actually be processed — independent of the main create/delete phase.

  • Public route: POST /applications/repository/webhooks/push/{repository_id} (full schema in section 3).
  • Redis: for delivery idempotency — webhook_delivery:{delivery_id}, 24-hour TTL, SET NX.
  • A new Celery task for async push processing: obtaining a fresh clone-token from auth, updating the git Secret on OpenShift, starting a new Build (the same action as a manual rebuild), and transitioning status to UPDATING / DEPLOYING until final resolution by regular polling.
  • Encryption mechanism for webhook_secret — shared with the mechanism used for other secrets.

Push processing logic

  1. Find the repository

    From {repository_id} in the URL, the repositories record is located.

  2. Check idempotency

    SET webhook_delivery:{X-GitHub-Delivery} NX EX 86400 in Redis → if duplicate: 200 {accepted:false, reason:duplicate_delivery}

  3. Verify signature

    HMAC signature check with the (decrypted) webhook_secret over the raw body → invalid: 401

  4. Check branch

    payload.ref against repositories.branch → mismatch: 200 {accepted:false, reason:branch_mismatch}

  5. Enqueue

    The async Celery task is queued, and 202 {accepted:true} is returned immediately.

Reminder The rest of the main flow — resolve with auto_deploy_on_push: true, saving webhook_id/webhook_secret at create time, and deletion at delete time — is part of the main create/delete flow; what's treated as a separate phase here is only the actual handling of incoming push events and the rebuild.
