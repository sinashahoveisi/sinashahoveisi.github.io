01 — Background & Context

Why We Benchmarked

dana-cli is the official command-line interface for the DanaIX IaaS cloud platform. It allows developers and DevOps engineers to manage servers, volumes, networking, and billing from the terminal without opening a browser.

The CLI was initially written in Python using typer + rich + httpx + pydantic. Before choosing a final distribution strategy, we evaluated three approaches: installing via pip, packaging as a native binary with Nuitka, and rewriting the CLI in Go.

Key question: For a cloud CLI used multiple times per day by DevOps engineers, every millisecond of startup time is friction. We benchmarked to answer: which distribution method delivers the fastest user experience, the smallest download, and the most practical build process?

Why startup time matters for a CLI

  • A DevOps engineer may run dana server list or dana server ssh web-01 dozens of times per day.
  • CLIs used inside shell scripts, CI/CD pipelines, and loops are invoked hundreds of times in sequence.
  • Any cold-start overhead above ~100 ms is perceptible and creates friction, especially for commands like --help that return instantly by design.
  • The benchmark was triggered by user feedback: "it takes a few seconds to show --help" after the Nuitka binary was built.

Distribution journey

Before this benchmark, the team went through several iterations:

  1. PyInstaller onefile — discarded. Extracts to a temp directory on every run, causing a 3–5 s cold start on every invocation.
  2. PyInstaller onedir — better startup, but must be shipped as a zip archive that the user must extract. Poor UX.
  3. Nuitka onefile — compiles Python to C, produces a real native binary. Tested in this benchmark. Still ~1.5 s startup.
  4. pip / pipx install — discovered to be faster than the Nuitka binary in practice. Included in this benchmark.
  5. Go rewrite — full rewrite of the CLI in Go using cobra. Included in this benchmark.
02 — The Three Builds

What Was Tested

pip / venv
Python 3.12.13 · typer + rich + httpx + pydantic
Primary distribution

Editable install into a virtualenv. Invoked as venv/bin/dana. Python interpreter loads .pyc bytecode cached by the OS on repeated runs.

Python binary
Nuitka onefile · compiled to C + linked
Rejected

Nuitka compiles the Python source to C and produces a single self-contained executable. No Python installation required on the target machine. Built with make build-local.

Go binary
Go 1.22 · cobra + resty · goreleaser
Recommended

Full rewrite of the CLI in Go using cobra for the command tree. Statically linked, no runtime dependencies. Built with go build -ldflags="-s -w" via Makefile.

Nuitka onefile trap: The ~1.4 s startup is not caused by Python code being slow — it is caused by Nuitka's onefile bootstrap, which decompresses the bundled payload into a temporary directory on every invocation. This overhead is essentially constant and cannot be optimised away without switching to onedir mode (which requires distributing a directory, not a single file).
Why pip is faster than Nuitka: When Python is already installed on the system, the OS caches .pyc bytecode files in memory between runs. The Python interpreter starts in ~20 ms, and warm subsequent imports are nearly free. The Nuitka binary, by contrast, starts a fresh extraction process every time — there is no OS-level cache benefit.

07 — Analysis

Root Cause Analysis

Why pip is faster than the Nuitka binary

This is counterintuitive. A compiled binary should be faster than an interpreted language — but not in this case. The key is how Python loads code:

  • Python compiles source files to .pyc bytecode on first import and caches them on disk.
  • On subsequent runs, the OS file cache keeps these .pyc files in memory, making imports nearly instantaneous.
  • The Python interpreter itself (/usr/bin/python3) is a standard system binary that stays warm in the OS page cache.
  • The Nuitka onefile binary must decompress its embedded payload into a temp directory on every invocation — this takes ~1.4 s regardless of how many times you run it, because there is no cross-invocation caching.
Nuitka onedir would be faster than onefile (~200–300 ms startup), but it requires distributing a directory instead of a single file. This trades startup speed for distribution complexity — the user must unzip and manage a folder. Neither option is ideal.

Why Go is fastest

Go compiles to a true native binary with no runtime extraction, no interpreter, and no dynamic library loading at startup. The entire binary is a single statically-linked ELF/Mach-O file:

  • The OS loads it directly into memory from the file system cache in milliseconds.
  • No Python interpreter startup (20–30 ms).
  • No .pyc bytecode compilation check on first run.
  • No import graph traversal of 10+ packages.
  • cobra's command parsing is compiled, not interpreted.

Why Nuitka API calls are so slow

The average API call time for Nuitka (15.6 s) is drastically higher than pip (5.2 s). The reason is that the ~1.4 s extraction overhead happens before the HTTP call even starts. With 5 runs at ~3 s startup each, plus network latency, the average compounds. The underlying Python HTTP stack (httpx) is identical — only the startup tax differs.

Summary of root causes

08 — Recommendations

Which Method for Which Use Case

pip / pipx install
Best for: developer machines with Python
  • Fastest setup: pipx install dana-cli
  • Good startup: ~25 ms warm
  • Easy to update: pipx upgrade dana-cli
  • pyproject.toml already ready to publish
  • Requires Python 3.11+ on target machine
  • 120 MB venv — acceptable for dev machines
Python binary (Nuitka)
Verdict: rejected
  • 6.9 min build time kills CI/CD iteration
  • 1.5 s startup is worse than pip
  • Larger binary than Go (19.3 vs 12 MB)
  • Only advantage: no Python required on target
  • For that use case, Go binary is strictly better
  • Do not use for this project
Go binary
Best for: end-user distribution
  • Fastest startup: ~8 ms cold, ~6 ms warm
  • Most consistent API calls: 1231 ms avg
  • Smallest binary: 12 MB single file
  • 8 s build time — fast CI/CD
  • No Python required on target machine
  • Ready for brew, apt, curl installer

Final recommendation: publish to PyPI as the primary distribution channel (zero-effort install for Python developers with pipx install dana-cli). Ship the Go binary via goreleaser for brew, apt, and curl-installer users. Drop the Nuitka pipeline entirely — it offers no advantage over either alternative.
09 — How to Reproduce

Running the Benchmark

Prerequisites

  • macOS arm64 (or Linux amd64/arm64 — adjust binary paths accordingly)
  • DANAIX_API_KEY set in dana-cli/.env or environment (for server list tests)
  • Python 3.11+ and Go 1.22+ installed

1. Build all three distributions

# Python venv (editable install)
cd dana-cli
python -m venv venv
source venv/bin/activate
pip install -e .

# Nuitka onefile binary (~7 min)
pip install nuitka
make build-local        # produces dist/dana-darwin-arm64

# Go binary (8 seconds)
cd ../dana-cli-go
make build              # produces dist/dana
Shell

2. Run the benchmark script

# From the project root (contains both dana-cli/ and dana-cli-go/)
DANA_VENV=/path/to/dana-cli/venv \
BUILD_PIP_MS=9000 \
BUILD_PY_MS=416000 \
BUILD_GO_MS=8000 \
bash benchmark.sh

# Output is saved to:
# benchmark-results-darwin-arm64-$(date +%Y%m%d).txt
Shell

3. Run on Linux for cross-OS comparison

# Copy script and binaries to a Linux host
scp benchmark.sh \
    dana-cli/dist/dana-linux-amd64 \
    dana-cli-go/dist/dana \
    user@linux-host:~/bench/

# Run on Linux (as root for accurate cold measurements)
ssh user@linux-host 'cd ~/bench && bash benchmark.sh'
# On Linux, the script drops page cache between cold runs:
# sync && echo 3 > /proc/sys/vm/drop_caches
Shell

Rebuild everything from scratch (RUN_BUILDS=1)

# Times and runs all builds before benchmarking
# Warning: Nuitka rebuild takes ~7 minutes
RUN_BUILDS=1 bash benchmark.sh
Shell

Bottom line: The Go binary wins on every measurable axis — fastest startup (8 ms), most consistent API performance (1231 ms avg), smallest single-file download (12 MB), and fastest build time (8 s). pip/pipx is the right choice for Python developers who prefer the pipx install dana-cli workflow. The Nuitka pipeline should be removed from the project — it is slower to build, slower to start, and larger than the Go binary.
