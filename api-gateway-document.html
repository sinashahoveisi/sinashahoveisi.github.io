01 — Problem Statement

What Problem Are We Solving?

Our system consists of multiple microservices. Each service receives requests with a JWT token in the Authorization header, and each service is currently responsible for validating that token independently.

Current state: Every microservice imports a JWT library, maintains its own validation logic, has access to the JWT secret or public key, and performs signature verification on every request. This means authentication logic is scattered across every service in the system.

Problems with Distributed JWT Validation

  • Code duplication — every team re-implements the same validation logic in potentially different ways.
  • Inconsistency — one service might check token expiry correctly while another skips a check, creating security gaps.
  • Key management surface — every service needs access to the JWT secret or public key, widening the blast radius of a key compromise.
  • Hard to rotate — changing the JWT algorithm or secret requires updating and redeploying every single service.
  • No rate limiting — there is currently no request throttling layer, leaving services exposed to abuse and overload.
  • No per-user throttling — even basic IP-level rate limits are absent, making DoS attacks trivial.
Figure 1 — Current state: distributed JWT validation, every service is responsible for auth

Rate Limiting Gap

Beyond authentication, there is currently no rate limiting in place. Without it, a single client (or attacker) can send unlimited requests, potentially degrading service for all users or triggering costly downstream operations. Rate limiting needs to be:

  • Per-IP — to block simple floods before they reach services.
  • Per-user (consumer) — to enforce API quotas tied to authenticated identities, not just network addresses, since many users may share the same IP (NAT, VPN, corporate proxy).
  • Per-route — some endpoints (e.g. /export, /report) are heavier and need tighter limits than simple GET endpoints.
02 — Solution Architecture

Centralized Auth via API Gateway

The solution is to move all authentication and rate limiting responsibility out of individual services and into a single gateway layer. This pattern is called Forward Auth (also known as External Auth).

Target state: The gateway intercepts every inbound request, forwards it to a dedicated Auth Service for validation, and only passes the request downstream after receiving a 200 OK. User claims extracted from the JWT are injected as headers into the upstream request. Microservices never see or validate a JWT — they only consume clean X-User-* headers they can trust.

Forward Auth Flow

Figure 2 — Target state: gateway intercepts every request, auth service validates and extracts claims, microservices receive clean headers

What the Auth Service Must Do

The auth service exposes a single lightweight endpoint (e.g. GET /validate). It receives the original request headers, validates the JWT, and returns either:

  • 200 OK with response headers containing user claims — the gateway injects these into the upstream request.
  • 401 Unauthorized — the gateway immediately rejects the request, the microservice is never reached.
# auth-service — /validate endpoint (Python / FastAPI example)
from fastapi import FastAPI, Header, HTTPException, Response
import jwt

app = FastAPI()

@app.get("/validate")
def validate(authorization: str = Header(...)):
    try:
        token = authorization.removeprefix("Bearer ")
        payload = jwt.decode(token, PUBLIC_KEY, algorithms=["RS256"])
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401)

    # Return claims as response headers — gateway will inject them upstream
    response = Response(status_code=200)
    response.headers["X-User-Id"]    = str(payload["sub"])
    response.headers["X-User-Role"]  = payload.get("role", "user")
    response.headers["X-User-Email"] = payload.get("email", "")
    return response

03 — Tool Comparison

Available Tools

Four tools are evaluated below. All four can implement the forward-auth + rate-limit pattern on Kubernetes, but they differ significantly in operational complexity, feature depth, and licensing model.

Kong Gateway
Kong Ingress Controller (KIC)
Recommended

Nginx-based API gateway with a rich plugin ecosystem. Can fully replace ingress-nginx. Configured via Kubernetes CRDs (KongPlugin, KongConsumer).

Pros
  • 60+ plugins — auth, rate limit, transform, tracing, canary
  • Per-consumer rate limiting (not just per-IP)
  • Admin API — config changes without restart
  • Active health checks on upstreams
  • Fully open source (Apache 2.0)
Cons
  • Needs PostgreSQL or DB-less config file
  • Higher operational complexity vs plain NGINX
  • Kong Manager UI is limited in OSS
  • More resources than ingress-nginx
NGINX Ingress Controller
Already deployed
Already in use

Kubernetes-native ingress controller based on NGINX. Supports forward auth via the auth-url annotation and basic rate limiting via limit-rps.

Pros
  • Already installed — zero new infrastructure
  • Simple annotation-based config
  • Minimal resource footprint
  • Well-documented, large community
Cons
  • Rate limit is per-IP only (no per-user)
  • Config changes require NGINX reload
  • No consumer or credential management
  • Advanced features require Lua snippets
Traefik Proxy
Traefik Ingress Controller
Alternative

Go-based reverse proxy with native Kubernetes auto-discovery. ForwardAuth middleware is built-in and requires almost no configuration.

Pros
  • ForwardAuth middleware is native, trivial to configure
  • Auto-discovers services via K8s annotations
  • Lightweight, low resource usage
  • MIT license (OSS)
Cons
  • Plugin ecosystem far smaller than Kong
  • Rate limit per-consumer requires Enterprise
  • Less mature for complex API management
Envoy / Istio
Service Mesh
Overkill for this use case

L7 proxy (Envoy) with a service mesh control plane (Istio). Intercepts all service-to-service traffic, enforces mTLS, and exposes an ext_authz filter for external authorization.

Pros
  • Intercepts both north-south and east-west traffic
  • mTLS between all services automatically
  • Deep observability (traffic, latency, errors)
  • Fully open source (Apache 2.0)
Cons
  • Extremely high operational complexity
  • Sidecar injection overhead on every pod
  • Steep learning curve for the entire team
  • Solving a simple problem with a very large tool

04 — Kong vs Envoy

Best Choice: Kong or Envoy?

Both Kong and Envoy can solve the forward-auth + rate-limit problem. The right choice depends on the scope of the problem you are actually solving.

Choose Kong when…
You need an API gateway, not a service mesh
You want per-consumer quotas and credential management
You want to add features via plugins, not custom Lua/WASM
Config needs to change at runtime without restarts
Your team can operate a gateway but not a full mesh
You need north-south traffic management (client ↔ service)
Choose Envoy / Istio when…
You need east-west auth (service-to-service mTLS)
You have a large platform team to operate the mesh
Observability across all inter-service calls is critical
You need traffic shifting between every pair of services
You have 50+ services and a dedicated SRE team
Auth is the least of your concerns — infra scale is
Verdict for this system: The problem is north-south API gateway concerns — authenticating external client requests, extracting user identity, and rate limiting. This is Kong's primary use case. Envoy/Istio would solve this problem but would also impose enormous operational overhead for features we don't need yet. Kong is the right tool here.
05 — NGINX Recommendation & Example

Using What We Already Have: ingress-nginx

Since ingress-nginx is already deployed on the cluster, it is the path of least resistance. It natively supports forward auth via a single annotation and can implement basic rate limiting. No new infrastructure is required.

When ingress-nginx is sufficient: If your requirements are simply (a) forward JWT validation to the auth service and (b) apply a basic per-IP rate limit, ingress-nginx covers both with a few annotations. No migration needed.

Example: Forward Auth + Rate Limit with ingress-nginx

# ingress-nginx — forward-auth + rate limiting
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: service-a-ingress
  namespace: default
  annotations:
    # 1. Forward every request to auth service before passing upstream
    nginx.ingress.kubernetes.io/auth-url: "http://auth-service.default.svc.cluster.local/validate"

    # 2. Take these headers from auth service response and inject into upstream request
    nginx.ingress.kubernetes.io/auth-response-headers: "X-User-Id, X-User-Role, X-User-Email"

    # 3. Basic rate limiting — per IP address
    nginx.ingress.kubernetes.io/limit-rps: "20"
    nginx.ingress.kubernetes.io/limit-connections: "10"

    # 4. Return 429 (not 503) when rate limit is exceeded
    nginx.ingress.kubernetes.io/limit-req-status-code: "429"
spec:
  ingressClassName: nginx
  rules:
    - host: api.yourdomain.com
      http:
        paths:
          - path: /service-a
            pathType: Prefix
            backend:
              service:
                name: service-a
                port:
                  number: 80

What the Microservice Receives

After the gateway processes the request, the upstream microservice receives the original request body and all original headers, plus the injected user headers from the auth service. The microservice never sees the raw JWT.

# Headers arriving at service-a after gateway processing
GET /service-a/orders HTTP/1.1
Host: service-a
# ── injected by gateway from auth service response ──
X-User-Id: 42
X-User-Role: admin
X-User-Email: user@example.com
# ── original request headers ──
Content-Type: application/json
# Note: Authorization header is NOT forwarded unless you explicitly add it
HTTP Headers
Security note: Microservices should trust X-User-* headers only from the gateway. Use a Kubernetes NetworkPolicy to ensure that direct pod-to-pod traffic (bypassing the gateway) is blocked, otherwise any service could forge these headers.
06 — Kong's Additional Capabilities

What Kong Adds Over ingress-nginx

The following capabilities are either unavailable or significantly harder to implement with ingress-nginx. They become relevant when the system grows and requirements evolve.

1. Per-User (Consumer) Rate Limiting

ingress-nginx can only rate-limit per IP address. Kong introduces a KongConsumer resource that maps an authenticated identity to a set of credentials and quotas. This means 100 users behind the same corporate NAT get their own individual quotas.

# Step 1 — define a consumer (one per user/service account)
apiVersion: configuration.konghq.com/v1
kind: KongConsumer
metadata:
  name: user-42
  annotations:
    kubernetes.io/ingress.class: "kong"
username: user-42

# Step 2 — rate-limiting plugin scoped to that consumer
apiVersion: configuration.konghq.com/v1
kind: KongPlugin
metadata:
  name: rate-limit-user-42
plugin: rate-limiting
config:
  minute: 60       # this user gets 60 req/min
  hour:   2000
  policy: redis    # shared across all Kong replicas
  limit_by: consumer
YAML

2. Dynamic Configuration via Admin API

Every Kong plugin, route, and consumer can be created, updated, or deleted at runtime via the Admin API — without touching any Kubernetes resource and without reloading NGINX. This is essential for operations like temporarily increasing a rate limit for a VIP user or disabling a route during an incident.

# Update a rate limit at runtime — zero downtime, no kubectl, no reload
curl -X PATCH http://kong-admin:8001/plugins/{plugin-id} \
  -d '{"config": {"minute": 200}}'

# Add a new plugin to an existing route — takes effect immediately
curl -X POST http://kong-admin:8001/routes/{route-id}/plugins \
  -d '{"name": "request-transformer", "config": {"remove": {"headers": ["Authorization"]}}}'
Shell

3. Request Transformer — Remove JWT from Upstream

By default, the raw Authorization: Bearer <token> header is still forwarded to the microservice even after the gateway validates it. With Kong's request-transformer plugin, you can strip it out so microservices truly never see the JWT.

apiVersion: configuration.konghq.com/v1
kind: KongPlugin
metadata:
  name: clean-upstream-request
plugin: request-transformer
config:
  remove:
    headers:
      - Authorization        # JWT never reaches microservice
  add:
    headers:
      - "X-Request-Id:$(kong.request.id)"  # add tracing ID
YAML

4. Active Health Checks

ingress-nginx only does passive health checking — it discovers a pod is unhealthy after a real request fails. Kong actively polls upstream pods at a configurable interval, removing unhealthy instances before any user request hits them.

apiVersion: configuration.konghq.com/v1beta1
kind: KongUpstream
metadata:
  name: service-a-upstream
healthchecks:
  active:
    http_path: /health
    healthy:
      interval: 5       # check every 5 seconds
      successes: 2
    unhealthy:
      interval: 5
      http_failures: 3  # 3 failures → remove from rotation
YAML

5. Observability Plugins (no extra infra config)

With ingress-nginx, wiring Prometheus metrics or distributed tracing requires manually patching NGINX config or deploying extra exporters. In Kong, these are first-class plugins applied in minutes.

# Prometheus metrics — Kong exposes /metrics automatically
apiVersion: configuration.konghq.com/v1
kind: KongClusterPlugin
metadata:
  name: global-prometheus
  labels:
    global: "true"    # applies to every route
plugin: prometheus

---
# OpenTelemetry tracing
apiVersion: configuration.konghq.com/v1
kind: KongClusterPlugin
metadata:
  name: global-tracing
  labels:
    global: "true"
plugin: opentelemetry
config:
  endpoint: "http://otel-collector:4318/v1/traces"
YAML

07 — Conclusion

Recommendation

Both ingress-nginx and Kong can implement centralized forward auth and basic rate limiting. The right choice depends on where the system is heading, not just where it is today.

Stay with ingress-nginx
If simplicity and speed of delivery are the priority
  • Zero new infrastructure to deploy
  • Forward auth works with 2 annotations
  • Per-IP rate limiting is sufficient
  • Team is already familiar with annotations
  • Future per-user limits are not a known requirement
  • Observability is handled at a different layer
Migrate to Kong
If growth and advanced API management are expected
  • Per-user / per-consumer rate limiting is needed
  • Config changes must take effect without any downtime
  • Multiple plugins are needed across different routes
  • Observability at the gateway layer is important
  • You anticipate canary deployments or A/B testing
  • Team is willing to invest in a slightly higher setup cost
Practical migration path: There is no need to choose everything up front. A low-risk approach is to start with ingress-nginx (it is already there, it works), implement the forward-auth pattern and basic rate limiting, and set a threshold: if per-user rate limiting or dynamic config changes become requirements, migrate to Kong at that point. The auth service code does not change — only the gateway configuration does.

Final Recommendation

Short term: implement forward auth and per-IP rate limiting using the existing ingress-nginx deployment. This solves the immediate problem (centralized auth + basic rate limiting) with zero new infrastructure and can be done today.

Medium term: if the system grows beyond 10–15 microservices, if per-user quotas become a product requirement, or if the team needs to change gateway config without touching Kubernetes manifests — plan a migration to Kong. The migration is not disruptive: Kong can be installed alongside ingress-nginx and routes migrated one by one.

Bottom line: ingress-nginx for simplicity and speed; Kong when you need per-user rate limiting, zero-downtime config changes, and a growing plugin ecosystem. The choice is not permanent — the auth service contract (validate JWT → return X-User-* headers) stays the same regardless of which gateway sits in front of it.
