Client Installation NEW in v2

How each build method is delivered to an end-user machine — not how the CLI talks to the DanaIX API. Choosing a distribution method is a trade-off between user experience (single file download vs. unzipping a folder), prerequisites (Python on PATH vs. none), and installation complexity.

pip / pipx install — Python Package
1
Prerequisites
Python 3.11+ must be on PATH. Recommended: install pipx first. 
python3 --version   # Python 3.11+
pip install pipx
pipx ensurepath
2
Install dana-cli
pipx creates an isolated venv automatically — no conflicts with system packages. 
pipx install dana-cli
# or from a local wheel:
pipx install ./dist/dana_cli-*.whl
3
Configure
Create .env in the directory where you run dana, or export env vars. 
echo "DANAIX_API_KEY=sk-..." > .env
echo "DANAIX_BASE_URL=https://api.danaix.com/iaas" >> .env
4
Update
pipx upgrade dana-cli
Files required on client: Python interpreter + site-packages (~136 MB on disk). Download size from PyPI is a ~500 KB wheel; pip fetches dependencies from the internet. System prerequisites: Python 3.11+ on PATH.

1
Prerequisites
None. No Python or runtime required on the client machine.
2

# INSTALL_DIR=/home/user/.local/bin bash install.sh  # custom path

Option B — GitHub Release (manual)

# Verify checksum

4
Option C — Homebrew
brew tap danaix/tap
brew install dana-cli
5
Option D — apt / rpm
# Debian/Ubuntu
sudo apt install ./dana-cli_amd64.deb
# Installs to /usr/local/bin/dana

Configure

Nuitka standalone — Directory Bundle
1
Prerequisites
None. No Python required. OS/arch must match the build (darwin arm64 or linux amd64, etc.).
2
Download and extract
curl -Lo dana-standalone.tar.gz \
  https://releases.danaix.com/dana/dana-darwin-arm64-standalone.tar.gz
tar xzf dana-standalone.tar.gz
# Produces: dana-darwin-arm64.dist/
#           ├── dana-darwin-arm64.bin   ← launcher
#           ├── libpython3.12.dylib
#           └── (other runtime libs)
3
Add to PATH
The entire .dist/ folder must stay together. Create a wrapper or symlink. 
# Option A: symlink the launcher
ln -s /opt/dana-dist/dana-darwin-arm64.bin /usr/local/bin/dana

# Option B: wrapper script
echo '#!/bin/sh\nexec /opt/dana-dist/dana-darwin-arm64.bin "$@"' \
  > /usr/local/bin/dana && chmod +x /usr/local/bin/dana
Files required: full .dist/ directory (80.5 MB). The folder must remain intact — do not move only the launcher. Warm startup is ~24 ms (as fast as venv); cold has one outlier (~1.1 s) caused by dylib cache warmup.

Compiler & Packaging Tool Comparison NEW in v2

Several tools exist for turning Python source into distributable binaries. This section explains why Nuitka and Cython were chosen, and where the alternatives fall short for a CLI tool like dana-cli.

Nuitka
Static Python-to-C compiler · static linking support
  • Highest language compliance — full CPython semantics
  • Onefile & standalone modes: no Python on target machine
  • Reasonable perf gains on compute-heavy code
  • Actively maintained; large user base
  • Onefile: ~1.1 s extraction penalty per invocation
  • ~7 min build time on M1 Pro
  • No low-level type optimisations (pure Python semantics only)
  • Standalone mode requires distributing a folder (80 MB)

Why chosen: Current release channel ships Nuitka onefile — it was the first approach that eliminated the Python dependency requirement while staying language-compliant. Onefile UX (single download) outweighed the startup cost for initial release.

Cython
Python-to-C extension compiler · CPython compatible
  • 20+ years of optimisation; thousands of production libraries use it
  • Full CPython compatibility across versions (3.x and PyPy/Pyston)
  • PEP-484 type annotations → static C types → real speed gains
  • Seamless C/C++ integration for future hot-path optimisation
  • Generate-once C code — reproducible across platforms
  • Paired with PyInstaller: ~1–2 min build (vs ~7 min Nuitka)
  • Requires PyInstaller for distribution (still a directory)
  • onefile via PyInstaller still extracts to temp dir on run
  • More complex build pipeline (Cython compile → C compile → PyInstaller)

Why chosen: Faster build pipeline than Nuitka (~2 min vs ~7 min), better future optimisation path via type annotations, and the onedir variant delivers venv-comparable warm startup (~130 ms) while remaining Python-dependency-free.

PyInstaller
Bundler (not a compiler) — used with Cython above
  • Mature; handles complex import graphs automatically
  • onedir mode: fast startup (~130 ms warm)
  • Well-known; broad ecosystem hook support
  • onefile: extracts to tmp on every run (~same penalty as Nuitka onefile)
  • Bundles a full CPython runtime — large directories
  • Not a compiler; no performance gain from PyInstaller alone
PyPy
Alternative CPython runtime with JIT compiler
  • JIT compilation: significant speed gains for long-running processes
  • Full Python language compliance
  • Good C/C++ extension integration
  • JIT warmup: no benefit for short-lived CLI invocations
  • Not CPython — limited compatibility with C extensions (httpx, pydantic)
  • Large runtime footprint; complex distribution
  • Non-obvious performance: may be slower than CPython for I/O-bound code

Not applicable for dana-cli: A CLI that exits in ~30 ms never reaches JIT warmup. PyPy's advantage is long-running server processes, not CLI tools.

mypyc
Static Python-to-C compiler · mypy-based
  • Good PEP-484 type support; reasonable perf gains
  • Native mypy type inference
  • No support for low-level / C-level optimisations
  • Opinionated type interpretation; reduced introspection after compile
  • Still requires Python on target (produces .so extensions, not standalone binary)
  • Incompatible with pydantic v2 dynamic models used in dana-cli
Numba
JIT compiler for numerical Python (LLVM-based)
  • Excellent for numerical / NumPy code
  • LLVM-backed — real native code generation
  • Only covers a subset of Python (numerical, array ops)
  • Large runtime dependency (LLVM)
  • No benefit for CLI I/O logic, HTTP clients, or string formatting

Not applicable: dana-cli has no numerical computation; Numba's scope is entirely mismatched.

Pythran
Static Python-to-C++ compiler for numerical subsets
  • Strong NumPy acceleration; C++ backend
  • Can be used as Cython NumPy backend
  • Limited to numerical / scientific code
  • No CLI or I/O primitives

Not applicable: same reasons as Numba.

Go (rewrite)
Full language rewrite — not a Python compiler
  • Native static binary — no runtime, no extraction
  • 7 ms cold start — optimal for CLI tools
  • 8 s build time — fastest CI/CD
  • 12 MB binary — smallest footprint
  • goreleaser: multi-platform releases in minutes
  • Full rewrite cost (one-time, already done)
  • Two codebases to maintain (Python for dev tooling, Go for distribution)

Best overall for distribution: wins on every measurable axis for end-user delivery.

Why Nuitka and Cython — not the others

Core requirement: dana-cli must run on a target machine with no Python installed. This immediately rules out PyPy (requires PyPy runtime), mypyc (produces .so extensions needing CPython), Numba and Pythran (scope mismatch), and plain pip (requires Python on PATH). Only Nuitka, Cython+PyInstaller, and a language rewrite satisfy this constraint.

Nuitka was chosen first because it offers the highest Python language compliance of any static compiler — it handles dynamic features, introspection, and complex import graphs that simpler tools miss. For a CLI with pydantic v2, typer, and rich, language compatibility is non-negotiable. The onefile mode provided the simplest UX (single file download, no extraction by the user). The ~1.1 s startup tax is a known trade-off accepted in the initial release.

Cython was added as a benchmark candidate because of its faster build pipeline (~2 min vs ~7 min) and its path to genuine performance improvements via type annotations. Cython has been the backbone of CPython-compatible binary distribution for over two decades (NumPy, pandas, lxml all use it). Paired with PyInstaller in onedir mode, it avoids the extraction penalty and delivers ~130 ms warm startup — acceptable for an interactive CLI.

The Go rewrite — which was already completed independently — turns out to be strictly better than any Python binary option for the distribution use case: 7 ms startup, 12 MB binary, 8 s build time, zero runtime requirements. The Python codebase remains valuable for developer tooling and rapid iteration (25 ms warm startup, fast pip install -e . rebuild cycle).

08

Root Cause Analysis

Why pip is faster than Nuitka (onefile)

This is counterintuitive. A compiled binary should be faster than an interpreted language — but not for onefile Nuitka. Python compiles source to .pyc bytecode on first import and caches it on disk. The OS file cache keeps these in memory between runs. The Python interpreter itself stays warm in the page cache. The Nuitka onefile binary decompresses its entire embedded payload to a temp directory on every invocation — there is no cross-invocation caching. The result: ~1.1 s constant overhead regardless of how warm the OS cache is.

Why Nuitka standalone matches venv on warm runs

Nuitka standalone avoids the extraction problem by shipping a directory. The .dist/ folder's shared libraries are loaded by the OS from the file cache just like any other binary. On warm runs the cold avg outlier (~1.1 s) disappears and median startup drops to ~25 ms — identical to pip. The trade-off: the user must manage a directory, not a single file.

Why Cython onedir sits at ~130 ms

PyInstaller's onedir mode bundles a complete CPython runtime and all shared libraries into _internal/. At startup, the launcher dlopen-loads this runtime from disk (~130 ms on M1 Pro cold, ~130 ms warm). This is slower than a native Go binary because there is still a Python interpreter initialisation step — Cython compiles the application logic to C, but the interpreter framework remains.

Why Go is fastest

Go compiles to a true native static binary. The OS maps it into memory in milliseconds. There is no interpreter, no runtime extraction, no import graph traversal, no bytecode compilation, and no dynamic library loading at startup. Cobra's command parsing is compiled AOT. The 7 ms cold average is close to the OS process-launch floor on Apple Silicon.

Build Startup cost source Optimisable?
Go binary OS binary load from page cache Already optimal (~7 ms floor)
pip / venv Python interpreter init + import graph + OS cache warmup Partial — lazy imports reduce to ~10 ms
Nuitka standalone dylib load from .dist/ (warm: same as venv) Yes — warm ≈ 24 ms
Cython onedir CPython interpreter init from _internal/ Partial — ~130 ms floor
Nuitka onefile Decompression of embedded payload to tmp on every run No — fundamental onefile limitation

Recommendations

Use case Best choice Why
Developer machine (Python available) pip / pipx 25 ms warm startup, fast rebuild, pipx upgrade for updates
End-user single download (brew, apt, curl) Go binary Smallest (12 MB), fastest (7 ms), zero deps, 8 s build
Python-only, no system Python, want fast startup Nuitka standalone 24 ms warm, no Python required; trade-off: 80 MB folder
Python-only, simpler build, folder acceptable Cython onedir ~2 min build (vs ~7 min), 130 ms startup, 40 MB folder
GitHub install.sh / packages (current) Nuitka onefile Already ships; accept ~1.1 s startup; consider migrating to Go
Shell scripts / CI loops Avoid Nuitka onefile ~1.1 s per invocation compounds; use Go or pip instead
Strategic recommendation: Migrate the primary release channel from Nuitka onefile to the Go binary via goreleaser. Keep the Python package on PyPI for Python developers. Retire the Nuitka pipeline from CI — it adds ~7 minutes per release and the Go binary is strictly better on every metric. Cython onedir is a viable middle ground if a Python-only distribution is required.

How to Reproduce

Prerequisites

# Python 3.12+, Go 1.22+, make, and DANAIX_API_KEY in dana-cli/.env
python3 --version   # 3.12.13
go version          # 1.22+

Build all variants

cd /Users/sina/Danaix/cli
cd dana-cli && source venv/bin/activate

# Cython onedir (~2 min)
make build-local-cython

# Nuitka standalone (~5–7 min)
make build-local-nuitka-standalone

# Nuitka onefile (~6.6 min) — build last; same output name as standalone
make build-local   # produces dist/dana-darwin-arm64

# Go binary (~8 s)
cd ../dana-cli-go && make build

Run benchmark

cd /Users/sina/Danaix/cli

DANA_VENV=/Users/sina/Danaix/cli/dana-cli/venv \
BENCHMARK_RESULT_FILE=benchmark-results-darwin-arm64-$(date +%Y%m%d).txt \
bash benchmark.sh

# Rebuild + run in one shot (warning: ~7 min for Nuitka)
RUN_BUILDS=1 bash benchmark.sh

# Skip Cython onefile (name conflict with onedir)
BUILD_CYTHON_ONEFILE=0 RUN_BUILDS=1 bash benchmark.sh

Linux cross-platform run

scp benchmark.sh dana-cli/dist/dana-linux-* dana-cli-go/dist/dana user@linux-host:~/bench/
ssh user@linux-host 'cd ~/bench && bash benchmark.sh'
# On Linux as root, the script drops page cache between cold iterations:
# sync && echo 3 > /proc/sys/vm/drop_caches

The Go binary wins on every measurable axis for end-user distribution: 9 ms cold start, 7 ms warm, 35 ms API average, 12 MB download, 8 s build time, zero runtime requirements. pip/pipx remains optimal for Python developers (25 ms warm, sub-10 s rebuild).

Among Python binary options, Nuitka standalone and Cython onedir are both viable when a Python-dependency-free build is required without the Nuitka onefile startup penalty — at the cost of distributing a directory instead of a single file. Cython's ~2 min build (vs ~7 min Nuitka) makes it the better choice for rapid iteration.

Next steps: (1) Migrate install.sh and GitHub releases to the Go binary. (2) Keep PyPI as the primary Python distribution channel. (3) Remove Nuitka from CI — no scenario where it outperforms either Go or pip. (4) Evaluate Cython onedir as a fallback distribution for environments where the Go binary is unavailable. (5) Run the same benchmark on Linux amd64 to complete the cross-platform picture.
